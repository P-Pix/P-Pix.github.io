Enjeu

Éviter les ambiguïtés dans les données d’un périphérique

Le protocole transporte plusieurs formes de données : une température, un ensemble de mesures IMU, une position GPS optionnelle ou un état radio. Le driver vérifie la réponse avant de construire un objet métier utilisable.

Une absence de position GPS n’est pas une panne de transport. Le modèle distingue les états métier normaux des erreurs, puis sépare transport, protocole et statut du périphérique pour permettre une réaction adaptée.

Choix techniques

Faire porter l’intention par les types

01 / MODÈLE

Nommer les données

ImuReading, GpsFix, RadioStatus et BatteryReading rendent les valeurs exposées explicites.

02 / ABSENCE

Utiliser std::optional

Une position indisponible se représente comme un état métier, distinct d’une exception de transport.

03 / HÉTÉROGÉNÉITÉ

Utiliser std::variant

Les lectures de natures différentes peuvent être réunies dans une collection en conservant leur type.

04 / ERREURS

Distinguer les causes

Les catégories transport, protocole et périphérique permettent de décider s’il faut réessayer ou propager une erreur.

Démonstration

Du codec aux scénarios de reprise

La démonstration incluse présente onze scénarios : CRC de référence, encodage/décodage, données des capteurs, reprise après timeout ou BUSY, statut d’erreur et rejet d’une séquence inattendue.

Tests du protocole et du driver avec mocksRésultat affiché dans cet extrait : 11 / 11 tests

Après compilation de la CLI selon le README, conserver le simulateur actif dans un premier terminal. Lancer ensuite le client C++ dans un second terminal en utilisant le même chemin de socket.

Terminal 1 · simulateur

./simulator/device_simulator.py --socket /tmp/edds_device.sock --verbose

Terminal 2 · client C++

./edds_cli --socket /tmp/edds_device.sock --command all
