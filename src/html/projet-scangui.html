Le problème

Faire évoluer une application native sans dupliquer le métier

La lecture d’un chapitre doit fonctionner depuis le système de fichiers, via une API locale ou depuis un cache offline. Si l’interface connaît chaque mode, la navigation et la progression se retrouvent dupliquées. `ScanDataSource` fournit donc un contrat unique au-dessus des implémentations locales et HTTP.

Le projet traite également le travail de fond : téléchargement, progression, pause, reprise, annulation et retry, sans bloquer la boucle GTK.

Le serveur local réalise son routage HTTP sur sockets POSIX, indexe les scans et sert images, progression, profils, favoris et recherche. Ce choix rend visible le fonctionnement d’une API sans dépendre d’un framework web moderne.

Décisions d’ingénierie

Préserver l’usage tout en structurant le code

01 / PORTABILITY

Trois modes, un contrat

L’interface consomme la même API en local direct, serveur local ou offline.

02 / RESPONSIVENESS

Queue de téléchargements

Les tâches longues exposent progression et annulation et ne bloquent pas le thread UI.

03 / SECURITY

Serveur borné au local

Contrôle anti path traversal, CORS configurable et refus des routes admin hors contexte local.

04 / DATA

PostgreSQL pour l’index

Scans, chapitres, pages, progression, favoris, historique et OCR disposent d’un modèle persistant.

Démonstration réelle

Validation du domaine sans dépendances graphiques

La capture exécute la suite légère couvrant session de lecture, repository JSON, source de fichiers, synchronisation offline, queue de téléchargement et parsing HTTP. La partie GTK reste séparée afin que le cœur soit testable sur une machine sans affichage.
